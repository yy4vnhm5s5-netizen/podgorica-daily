# Decisions Log — Gradom.me Platform

This is the historical decision log for the project: architectural, infrastructural, and product decisions made after project start, with reasoning and consequences. It complements `docs/adr/` — formal ADRs remain the authoritative, structured record for material architectural decisions per `AGENTS.md` §30; this log captures the same class of decision in a running chronological format, plus decisions that don't warrant a full numbered ADR (e.g. deployment-platform choice, operating-rule agreements).

**Sourcing note (added after a self-review pass):** none of this repository's ADRs (`docs/adr/*.md`) contain an explicit "Alternatives Considered" section — they follow a Context/Decision/Consequences format only. Where an entry below has an "Alternatives Considered" field, it is **my inference from the ADR's Context/Decision text**, not a quotation of an explicit ADR section, and is labeled as such. Dates are taken directly from each ADR's own `Date:` field where one exists; entries without an ADR use the best-available session-level date.

Entries are ordered oldest to newest.

---

## Modular monolith architecture

- **Date:** 2026-07-17 (ADR 0001's stated date)
- **Decision:** Build Gradom.me as a modular monolith with strict inward-pointing dependency direction (presentation → application → domain; infrastructure → application/domain contracts), rather than microservices.
- **Reason (from ADR 0001's Context):** the project "needs independently maintainable capabilities while its early operational footprint remains small," and requires that "modules [not] access each other's persistence implementations."
- **Alternatives considered:** *Inferred, not stated in the ADR* — the ADR does not name microservices explicitly, but AGENTS.md §35 elsewhere states "Extract a service only when the modular-monolith boundary has a demonstrated operational need; do not preemptively distribute the system," which is consistent with a distributed/microservices alternative having been implicitly rejected as premature.
- **Consequences (from ADR 0001):** deployment and operations stay simple during early delivery; module boundaries remain explicit and testable before extraction is ever needed; cross-module changes require contract design rather than direct imports or table access; a future service extraction has a defined ownership boundary but is not assumed prematurely.

## Collector/reader separation for all external data

- **Date:** 2026-07-17 (ADR 0007's stated date, generalized to every subsequent provider)
- **Decision:** No visitor request may ever invoke live scraping or a live provider call (except Weather, see below). All external data is written by out-of-band collectors to an atomically-updated JSON cache; application code only reads that cache.
- **Reason (from ADR 0007's Context):** "Podgorica Daily needs official planned power-outage information without making visitor requests scrape the CEDIS website... Source outages must remain available when collection fails, while malformed or suspicious empty parses must never erase a valid snapshot."
- **Alternatives considered:** *Inferred, not stated in the ADR* — an on-demand, per-request fetch-and-cache model is the natural alternative, and the ADR's emphasis on bounded retries, timeouts, and "never erase a valid snapshot" language implies that direct-from-request fetching was considered and rejected as unsafe, though the ADR does not name it explicitly.
- **Consequences (from ADR 0007, generalized to the pattern):** live cards show official attribution, source status, and last successful update time; stale records remain readable with an explicit stale notice; parsing is conservative (missing/malformed values keep raw source text rather than invented values); every new data source requires the full collector chain before any UI can use it, and data is only ever as fresh as the last successful collector run.

## Weather is the one exception to the collector pattern

- **Date:** 2026-07-17 (ADR 0003's stated date)
- **Decision:** Weather (Open-Meteo current conditions) is fetched live during server rendering, not through a collector/cache. Responses are cached for ten minutes at the HTTP layer, but this is a short-lived response cache, not the collector/snapshot pattern used elsewhere.
- **Reason (from ADR 0003's Context/Decision):** the product needed "a source with a server-consumable current-conditions endpoint, no client-side credentials, documented weather variables, and an exit path if reliability, licensing, or operational requirements change." The decision explicitly keeps the provider payload isolated to `src/modules/weather/infrastructure` and requires every response to be Zod-validated with a safe error/empty state on failure.
- **Alternatives considered:** *Inferred, not stated in the ADR* — treating Weather like every other provider (collector + long-lived file cache) is the natural alternative; it was not adopted, plausibly because Open-Meteo requires no API key and per-request freshness has direct product value for a "current conditions" feature, but the ADR does not state this trade-off explicitly.
- **Consequences (from ADR 0003):** the first weather capability ships without storing an API key or exposing a provider request to the browser; a malformed/missing/non-success response becomes a safe error or empty state rather than a provider error shown to users; Open-Meteo does not remove the need for future availability monitoring or an adapter replacement strategy. Weather remains the only module without a `collect:*` script or scheduler entry.

## Daily Overview is deterministic, not AI-generated

- **Date:** 2026-07-17 (ADR 0005's stated date)
- **Decision:** The Daily Overview summary is generated by a pure, deterministic domain generator over a normalized `CityDataSnapshot` — no generative model, language model, or usage-based generation API is used.
- **Reason (quoted from ADR 0005's Context):** "Podgorica Daily needs a readable daily city overview without generating or inventing information. The project must remain zero-cost for this capability and must not use external generative services, language models, generative APIs, or any usage-based content-generation service. Visitors must never trigger scraping or provider refreshes while loading a page."
- **Alternatives considered:** LLM/generative-service-generated summaries — this alternative is named and explicitly rejected in the ADR's own Context (see quote above), so unlike most other entries in this log, this one *is* sourced directly from explicit ADR text, not inferred.
- **Consequences (from ADR 0005):** the summary "cannot invent, guess, or mention unavailable categories because it only evaluates typed available data"; it remains deterministic, auditable, and free of usage-based generation costs; a future scheduler/cache implementation can be added behind the existing provider contract without changing the generator or UI; the ADR also notes the *initial* mock cache and its visible demo notice had to be replaced before Daily Overview could be represented as live city information — confirmed done, per `AGENTS.md`'s current description of Daily Overview as consuming real cached data today.

## Event quality pipeline before dedup/caching

- **Date:** 2026-07-17 (ADR 0012's stated date)
- **Decision:** Every normalized Event candidate passes through deterministic quality validation (`accepted`, `acceptedWithWarnings`, or `rejected`, with typed rule codes and an explainable 0–100 score) before deduplication and cache writes; rejected events are never exposed publicly.
- **Reason (from ADR 0012's Decision):** to make quality outcomes explainable and policy-driven rather than ad hoc — "No content is rewritten, invented, or AI-classified," and rejection/warning behavior is driven by explicit configured policy (`EVENT_QUALITY_MAX_PAST_DAYS`, `EVENT_QUALITY_MIN_SCORE`, count-drop and warning-rate thresholds, etc., "all values validate at startup").
- **Alternatives considered:** *Inferred, not stated in the ADR* — per-provider ad hoc validation, or no validation at all, are the natural alternatives given five heterogeneous sources exist; the ADR's emphasis on a single shared, typed, policy-driven pipeline implies these were rejected for consistency and explainability, but this is my inference, not ADR text.
- **Consequences (from ADR 0012):** availability (`fresh`/`stale`/`unavailable`/`disabled`) is kept separate from quality health, with an explicit precedence order (disabled wins, then unavailable, then failing, then degraded, otherwise healthy); a zero-valid refresh result retains the previous valid cache; legacy (v1/v2) snapshots without diagnostics remain readable with safe defaults; new Event sources must integrate with this shared pipeline rather than inventing their own validation.

## City-prefixed routing with a distinct platform homepage

- **Date:** ADR 0022 dated 2026-07-22; ADR 0023 (which supersedes the root-route/sitemap portion of 0022) dated 2026-07-26
- **Decision:** All city content lives under canonical city-prefixed routes (`/podgorica`, `/budva`, ...); `/` is a separate, self-canonical Gradom.me platform homepage that lists active cities and links into them, rather than rendering (or redirecting to) any one city's dashboard.
- **Reason (from ADR 0022's Context, and ADR 0023's Context which is the more direct reason for the homepage-specific part):** ADR 0022: "Root-level content routes make the current city implicit and would require a public URL migration when another city is activated." ADR 0023 (superseding the root-route portion): "Rendering the Podgorica dashboard at `/` creates a second crawlable presentation of the same city and makes the platform itself invisible."
- **Alternatives considered:** ADR 0022 itself supersedes ADR 0021's prior root-level canonical routing and legacy-redirect policy — so one real, named alternative (ADR 0021's approach) genuinely was tried first and explicitly superseded, this is sourced fact, not inference. ADR 0023 also implicitly considered and rejected "keep `/` as the city dashboard with a redirect or switcher," per its stated problem framing, though that specific alternative phrasing is my inference.
- **Consequences (from ADR 0022 and ADR 0023):** adding an active city requires a registry entry and approved data coverage, with generic city routes/metadata already existing; inactive/unknown city slugs resolve through the normal not-found path; provider-specific Podgorica collectors remain scoped to Podgorica until separate source coverage is approved; two homepage-shaped surfaces now exist (`/` and `/<city>`) with distinct metadata/structured data.

## Railway as the active production deployment platform

- **Date:** documented in this project's memory on 2026-07-27 (session date); the underlying operational decision's original date was not stated by the owner and is not otherwise recoverable from the repository.
- **Decision:** Railway is the active production deployment for Gradom.me, using a single `web` service with a persistent volume at `/app/.runtime` and Railway cron trigger services calling authenticated internal refresh endpoints — not the self-hosted VPS + Docker Compose + shell-scheduler topology, even though both remain documented in the repository.
- **Reason:** owner-stated operational fact; the specific reasoning (cost, portability, operational simplicity) was not elaborated by the owner beyond confirming Railway is what's live. `docs/DEPLOYMENT_RAILWAY.md` independently frames Railway as "a managed, portable first target," consistent with this choice, but that document does not itself assert Railway is definitely the chosen production target — that confirmation came directly from the owner, not from repository text.
- **Alternatives considered:** the self-hosted Ubuntu VPS with Docker Compose and Caddy, which is fully documented as the "recommended first production target" in `docs/DEPLOYMENT.md` but is not what's actually running. This is a real, named, documented alternative, not an inference.
- **Consequences:** the VPS documentation remains accurate as a *capability* of the codebase but must not be assumed to describe current production behavior; anyone debugging production must reason in terms of the Railway topology (single web service, mounted volume, cron-triggered refresh endpoints); pushing to the tracked branch auto-deploys to Railway (`docs/DEPLOYMENT_RAILWAY.md`), so push permission is operationally equivalent to deploy permission on this project — see [CLAUDE.md §9](CLAUDE.md#9-railway-production-notes-owner-confirmed-authoritative) and [CLAUDE.md §16](CLAUDE.md#16-git-workflow).

## Operating rules for AI-assisted development sessions

- **Date:** documented in this project's memory on 2026-07-27 (session date); rules were stated by the owner across multiple points in this session, exact original adoption date not provided.
- **Decision:** All coding sessions on this repository (human- or AI-driven) must: explain scope before changing code; keep changes minimal and focused; avoid unnecessary refactoring; run relevant tests after changes; never modify unrelated files; never commit, push, deploy, or run live production collectors without explicit per-action instruction; use a direct Git workflow (commit → push → verify, with owner approval as a gate before commit) rather than feature branches/PRs by default; verify claims against primary sources rather than prior summaries (Repository First Rule); and end significant documentation/design work with a structured self-review (Documentation & Design Self-Review Rule).
- **Reason:** the project owner wants tight control over side effects given this is a real production system serving real users, wants AI-assisted sessions to be auditable and reversible rather than autonomous, and — based on issues surfaced during an explicit self-review pass on 2026-07-27 (stale/unverified claims, duplicated facts, an inaccurate ADR reference) — wants future sessions to verify against primary sources and self-check before treating documentation work as finished.
- **Alternatives considered:** none stated — these were given directly as standing operating rules, not as a choice among alternatives.
- **Consequences:** every session must pause for explicit approval before commits, pushes, deployments, or live collector runs; the full canonical rule text lives in `CLAUDE.md` §14 (Working Agreement), §15 (Repository First Rule), §16 (Git Workflow), and §18 (Documentation & Design Self-Review Rule) — this log entry summarizes them but is not their source of truth.

## Budva added as second active city with a partial capability set

- **Date:** Budva-CEDIS-related code changes landed by commit `e65bbbb` ("fix: enable Budva CEDIS refresh and capability-based services") on 2026-07-26 per `git log`; the original decision to activate Budva itself is not independently dated in the repository and may predate that commit.
- **Decision:** Budva is active with `electricity, weather, goingOut` capabilities, explicitly excluding `water`.
- **Reason:** no supported water-notice provider exists for Budva yet — capabilities are only turned on once genuine, approved provider coverage exists for that city (owner-confirmed; consistent with the "How to Add a New City" guidance in `CONTRIBUTING.md`, which itself reflects this precedent rather than the other way around).
- **Alternatives considered:** *Inferred, not stated in any document* — reusing the Podgorica VIK water provider or a generic/placeholder water status for Budva would be the natural shortcut; it was not taken, consistent with the project's stated principle to never fabricate or infer city information beyond what a real source provides (AGENTS.md §2), though no document explicitly frames this as a considered-and-rejected alternative for Budva specifically.
- **Consequences:** the Budva dashboard has a visibly smaller capability set than Podgorica's, which is correct and expected; this must not be "fixed" by inventing a water source, only by a genuine future provider decision (tracked as a Long Term / not-scheduled item in `ROADMAP.md`); the same `e65bbbb` change that enabled Budva CEDIS refresh is the area directly implicated in the current Priority 1 production issue (see `CURRENT_STATUS.md`).
